# AI receptionist — decisions made during the build

Date: 2026-11-16 · Branch: `feat/ai-receptionist`

This is the record of every decision the implementer made on the owner's
behalf while building the plan in `2026-11-16-ai-receptionist.md`, copied from
the build ledger. Each ruling says what was decided, why, and what it costs if
it turns out to be wrong. Nothing here was chosen by the owner; any of it can
be revisited.

## Rulings, in the order they were made

- Setup: Ruling: work in place on branch feat/ai-receptionist, no separate worktree — the owner-approved plan says to create the branch in Task 1 and the spec/plan are untracked files in this checkout — cost if wrong: the owner's checkout sits on the feature branch until `git checkout master`.
- Setup: Ruling: run every command with Node 22.20.0 from nvm — the shell default is Node 26.5.0, where the existing twilio dependency fails to load (7 suites fail at baseline); .nvmrc and package.json engines both require Node 22–24 — cost if wrong: none for the code; anyone running tests on Node 26 sees failures that predate this work.
- Setup: Ruling: commit the spec and plan (docs/superpowers/) as the branch's first commit; leave reports/ and research_notes/ untracked — the design skill expects the spec in the repo; the research folders are the owner's to keep or discard — cost if wrong: one docs commit to drop.
- Task 3: Ruling: a missing From is counted against the daily limit as the literal "anonymous", same as a blocked caller ID — the plan only covered a non-E.164 string; an undefined key would never match a stored row — cost if wrong: all number-less callers share one daily limit of 3 agent calls, after which they get today's behaviour.
- Task 4: Ruling: the webhook branch lives in twiml.agentTwiml({body, provider, connection}) → string|null, and the router test drives the real router over HTTP — the plan sketched req/res-style router tests, but no existing test drives the router and an HTTP test proves the wiring — cost if wrong: none functional; one extra exported function.
- Task 4: Ruling: the login-bypass list moved from index.js into security.isTwilioWebhook(req) so it can be tested (index.js starts a server on require and cannot be loaded in a test) — every previous path is covered by a test — cost if wrong: a path dropped from the list would make Twilio get a 401; the test list guards the ten paths.
- Task 4: Ruling: when the fallback itself fails inside endedHandler (provider lookup throws), the caller hears a fixed "we'll call you back" <Say> and a hangup instead of an HTTP 500 — the plan did not cover this; a caller must never get an error — cost if wrong: a caller hears a short apology instead of Twilio's default error message.
- Task 6: Ruling: the two tools are `strict: true` WITHOUT `eager_input_streaming` (the plan asked for both) — eager streaming turns off the API's input validation and only helps large tool inputs; these inputs are a few words, so the schema guarantee is worth more — cost if wrong: none measurable; tool inputs arrive when the block closes, as they would anyway at this size.
- Task 6: Ruling: added WRAP_UP_LINE to prompt.js for the maximum-call-length ending — the plan named "a fixed wrap-up line" without defining it — cost if wrong: wording only.
- Task 6: Ruling: the knowledge draft contains 11 TODO(owner) gaps (fee collection, steps after the first call, new-authority policy, other equipment, regions, insurance minimums, extra documents, three objections) — the website does not state them and the spec forbids inventing facts — cost if wrong: none; launch gate 6 requires the owner to clear them.
- Task 7: Ruling: the lookup filler is spoken by the app (agent.LOOKUP_FILLER, only when the model streamed no text in that request) and the goodbye is a required `goodbye` input of end_call that the app speaks — the plan had the model say both as text in the same turn as the tool call, but on Opus 5.5 / Sonnet 5.5 text written just before a tool call can come back as an empty progress-update thinking block, so the caller could hear silence during a lookup and no goodbye before the hangup — cost if wrong: if a model also writes its own goodbye as text, the caller hears two goodbyes; the prompt tells it not to.
- Task 7: Ruling: end_call's tool_result is appended to history before the turn ends (the plan only said "the loop stops") — a tool_use without its result would make the next request invalid if the caller interrupts the goodbye and the call continues — cost if wrong: none.
- Task 7: Ruling: an end_call with an invalid outcome is returned to the model as an is_error tool_result instead of ending the call — strict tools should prevent it, this is the guard if the API ever does not — cost if wrong: one extra model request.
- Task 7: Ruling: prewarm goes to the standard endpoint without betas/fallbacks (max_tokens: 0 with fallbacks is unverified); system, tools, effort, thinking and speed match the live request so the cache entry is the same — cost if wrong: the first turn of a call pays a cold cache write (a little latency), nothing else.
- Task 8: Ruling: the silence check starts after the estimated time the agent needs to finish speaking (speakMs(text) + 12 s), not 12 s after the text is sent — Twilio does not report when speech ends, and a 12 s timer from the moment of sending would fire while the 12-second greeting is still playing — cost if wrong: the "are you still there?" comes a few seconds later than a caller might expect.
- Task 8: Ruling: a call that ends on silence is saved as `lead` when the caller spoke earlier in the call and `abandoned` only when they never spoke (the plan said always `abandoned`) — someone who talked and then went quiet should still produce a card with a summary — cost if wrong: the owner sees a card for a caller who drifted away.
- Task 8: Ruling: if the caller talks over the goodbye, the pending hang-up is cancelled and the conversation continues, with a one-line note to the model that the call is still live — the plan did not cover it; hanging up on someone mid-sentence is the worse failure — cost if wrong: a call stays open until the caller's next turn or the silence check ends it.
- Task 8: Ruling: session.handle() returns a promise and all turns and interruption bookkeeping run through one queue — needed so an aborted turn's partial text is recorded before the next turn starts — cost if wrong: none.
- Task 8: Ruling: 5 s after sending `end`, the session closes the socket itself if Twilio has not — backstop only; Twilio's docs say `end` returns control to Twilio — cost if wrong: none (the call has already been handed back).
- Task 9: Ruling: the upgrade signature is accepted when it validates against either the wss:// or the https:// form of the URL — Twilio's onboarding page (read 2026-11-16) says only "the request URL" and gives no sample; both forms still require the account's auth token — cost if wrong: if Twilio signs some third form, every agent call is refused with 403 and falls back to today's behaviour; rollout step 3 (first test call) reveals it immediately.
- Task 9: Ruling: connectionWebhooks.authenticateConnectionWebhook now goes through the new loadConnectionAuth, which decrypts the connection's credentials before the AccountSid comparison instead of after — same outcome for valid and forged requests; a forged request against a connection whose credentials cannot be decrypted now gets 503 where it got 403 — cost if wrong: none for callers; existing suite passes unchanged.
- Task 9: Ruling: Twilio's onboarding page lists a prerequisite the plan did not have: the account must accept the ConversationRelay AI terms in the Twilio console (Privacy & Security) — added to the rollout checklist in Task 13 — cost if wrong: none.
- Task 10: Ruling: a `failed` call in which the caller spoke IS emailed (subject "Agent failed, call back: …") and counts in the unread Leads badge — the spec said failed calls appear in the softphone only, but the fallback line the caller hears promises "a dispatcher will call you back shortly", and the spec's own anti-goal is a call that fails silently — cost if wrong: the owner gets an email for calls where the agent broke; that is the case they most need to hear about.
- Task 10: Ruling: if saving the card fails (database down), the lead email is still sent, built from the same fields — the plan only covered the email failing; losing a lead because of a database error is worse than an email without a card — cost if wrong: an email arrives for a call that has no card in the softphone.
- Task 10: Ruling: the summary request sends no explicit effort and no refusal fallback (it uses messages.parse on the standard endpoint); a refusal, a cut-off answer or an API error all produce a card that says "Summary unavailable — read the transcript." — keeps the after-call step simple; the transcript is always saved — cost if wrong: an occasional card without a summary.
- Task 11: Ruling: the unread-leads number is served by a new GET /leads/count instead of adding `leads` to GET /activity-counts — the existing activityViews test asserts that response exactly, and the global constraint is that existing behaviour and tests stay unchanged — cost if wrong: the softphone makes one more small request when it refreshes its badges.
- Task 11: Ruling: GET /leads returns an empty list (and /leads/count returns 0) when the receptionist_calls table does not exist yet — the code can be deployed before the migration runs without the softphone showing an error — cost if wrong: a missing table is silent in the UI; it is still an error in the voice path's logs.
- Task 12: Ruling: "Call back" dials at once through voice.dial and keeps the Leads view open (it does not switch to the Calls view the way Contacts' dial button does) — the owner needs the script in front of them during the call; the dial card on the left still shows the call — cost if wrong: one click fewer than the owner may expect before a call starts.
- Task 12: Ruling: step 5 (look at it in a browser) was done against a throwaway stub backend serving the built frontend with three sample leads, not against the real app and a development database — the repo's .env points at real Twilio credentials and a database I should not start against; the stub exercised the nav badge, three card types, the transcript toggle, Mark done, and a 420px-wide layout, with no console errors — cost if wrong: differences between the stub's JSON and the real API would not show; the API shape is covered by routes.test.js.
- Task 12: Ruling: the carrier line is hidden on a non-lead card that has no MC or USDOT number — "No authority yet" under a broker's message reads as a fault — cost if wrong: none.
- Task 13: Ruling: the simulation uses a canned FMCSA answer (MC 196057 / USDOT 295917 found, everything else no match) instead of the live public lookup — keeps a run repeatable and limits it to Claude API requests — cost if wrong: the simulation does not exercise the real lookup; that is unit-tested and was run live once during Task 5.
- Task 13: Ruling: the script's logic is exported and unit-tested with a scripted caller and agent (the plan only asked to verify the --yes guard) — otherwise none of the script would have run before the owner pays for a real run — cost if wrong: none.
- Final: Ruling: what Twilio reports when this server closes the socket itself (a refused connection, or a crash mid-call) is not determinable here; if it reports the session as completed, the caller is hung up on with no fallback — the code stands; "restart the app in the middle of a test call" was added to rollout step 5 — cost if wrong: a caller on the line during a crash or deploy is dropped.
- Final: Ruling: "✓ verified" reflects the FMCSA USDOT registration record plus the caller's confirmation, not that the MC operating authority is active (the spec said "authority status") — stands; recorded in the spec's change list — cost if wrong: a carrier with revoked authority can show as verified; the dispatcher's own vetting still applies.
- Final: Ruling: there is no cap on total spend from many different numbers calling (the spec defines a limit per number only) — stands; the feature switch is the stop — cost if wrong: a burst of spam calls from rotating numbers each costs up to 8 minutes of ConversationRelay and model time.
- Final: Ruling: transcripts and summaries are kept indefinitely; the spec is silent on retention — stands; raised with the owner — cost if wrong: personal data accumulates in receptionist_calls.
- Final: Ruling: whether the greeting's wording satisfies every state's rules on transcription consent is a legal question — stands; for counsel, as the research report said.
- Final: Ruling: the status-change route has no cross-site request forgery protection, the same as every existing Basic-auth POST route in this app, and needs an unguessable call SID — stands — cost if wrong: a malicious page open in the operator's browser could mark a known card done.
- Final: Ruling: knowledge document accuracy, persona, voice quality, noisy-cab interruption tuning, whether Twilio signs the wss or https URL, whether `end` cuts queued speech, and whether the voice ID is accepted are all left to the owner's test calls (rollout steps 4-7) — none can be judged without a live call.

## Fixed after the whole-branch review

An independent reviewer read the branch once all thirteen tasks were done. It
found no critical problems and six important ones; these were fixed test-first.

- (1) Twilio's withheld-caller-ID pseudo-numbers were treated as real numbers — phone.test.js "callableNumber", session "pseudo-number is treated as unknown", alertEmail and leadCard pseudo-number tests RED→GREEN, suite 341/341
- (2) the call was held in memory until an unbounded summary request returned — finalize "the call is saved before the summary is requested", "a slow summary cannot hold the card back", "emailed at once, before any summary", summary "one bounded attempt", store "updateSummary", "countNew also counts a call that was never closed" RED→GREEN, suite 341/341
- (3) the stall watchdog only covered time to first text — agent "goes quiet after it started speaking", "tool-only reply that takes seven seconds", "runs past twenty seconds" RED→GREEN, suite 341/341
- (4) a carrier the caller rejected stayed on the card as verified — agent "the latest lookup wins", session "a carrier the caller rejected does not stay on the call", finalize "a looked-up carrier the caller did not confirm is not shown as verified" RED→GREEN, suite 341/341
- (5) answering a call waited on the database with no bound — twiml "a routing decision that hangs gives the call today's path within two seconds", "a call record that lands after the deadline is discarded" RED→GREEN, suite 341/341
- (6) "are you still there?" could be spoken over a talking caller, and a stray keypress switched the silence check off — session "a caller who is still talking is not asked", "a stray keypress does not switch the silence check off", twiml partialPrompts RED→GREEN, suite 341/341. NOT VERIFIED against Twilio: that partial prompts arrive as expected with partialPrompts="true"; added to rollout step 4.
- (7, re-graded from Minor) an invalid time-zone setting failed every inbound call and an exception in the socket handler was uncaught — config "an invalid time zone falls back", server "an error while handling a message is logged", "an error while starting the session refuses the socket" RED→GREEN, suite 341/341
- (8, re-graded from Minor) the card and email hid the caller ID when the caller gave another number — leadCard "the caller ID is shown beside a different number", alertEmail "the caller ID is listed beside" RED→GREEN, suite 341/341
- (completing the Task 7 ruling) the lookup tool's description still told the model to speak the filler — prompt "the lookup tool does not tell the model to speak the filler" RED→GREEN; the double filler for two lookups in one reply was fixed with it (agent "the filler is spoken once").
- (with 2) the database-down email carried no transcript — finalize "transcript included", alertEmail "with no summary the email carries the transcript" RED→GREEN.

## Review findings left as they are

Small issues the reviewer raised that were not changed. Each is a candidate for
a follow-up.

- the outcome and callback promise from end_call are dropped if the caller talks over the goodbye and then hangs up; the summary normally restores them.
- a caller turn still queued when the socket closes runs one model request whose reply nobody hears.
- keyed digits not yet submitted are lost at hangup; caller speech after a failed turn is not recorded.
- calling hours with start >= end silently mean "always closed"; thinking "off" on Sonnet with effort xhigh/max returns an API error on every turn.
- the WebSocket upgrade listener closes every non-receptionist upgrade request, even with the feature off (no known client uses one).
- the browser notification names the newest "new" card of any outcome.
- no test runs the server, session and agent together against the real SDK stream; the reviewer's probe did, once, and it worked.
